# Expaghetti Architecture Review & Planning

This document outlines the proposed architectural improvements and refactoring plan for the **Expaghetti** Lua regular expression engine. The focus is on simplifying state management, consolidating loosely structured metadata, reducing duplicated code, and clarifying naming conventions across the parser and matcher, aligning with the goals of Workflow 12.3.

## User Review Required

## Internal Architecture & Algorithm Audit

> [!IMPORTANT]
> This workflow is **not** intended to add new regex features or change external behavior. Its purpose is to perform a critical review of the engine's internal architecture, algorithms, AST representation, and data structures, identifying opportunities to simplify, optimize, or modernize the implementation while preserving functionality.

Perform a comprehensive review of the engine with the following goals:
- Identify unnecessary complexity or redundant state.
- Simplify AST node representations where possible.
- Improve naming consistency across the parser, matcher, and AST.
- Reduce memory usage by eliminating unnecessary fields.
- Review matching algorithms for potential optimizations.
- Improve maintainability without changing external behavior.

Any proposed change should satisfy at least one of the following:
- Simpler implementation.

## Proposed Changes

### Immediate Algorithmic & Architectural Refactors

During the review, several clear opportunities for immediate improvement were identified:

#### [MODIFY] `expaghetti/parser.lua` & `expaghetti/tokenizer.lua` (Tokenization Overhead)
- **Issue**: Currently, `parser.lua` converts the entire regex string into a Lua array of single characters, and then `tokenizer.lua` converts *that* array into an array of token objects (tables with `raw`, `value`, `isEscaped` fields). For long expressions, this causes massive, unnecessary memory allocations.
- **Solution**: Refactor `Tokenizer` to operate directly on the character array (or string iterator) and avoid allocating a new table for every single literal character. We can represent literal tokens more efficiently or combine the tokenization and parsing phases slightly to skip the intermediate table generation.

#### [MODIFY] `expaghetti/matcher.lua` & `expaghetti/ast.lua` (Target String Representation)
- **Issue**: The matcher currently splits the target string into an array of 1-character strings before execution (`splitStringByEachChar`), causing massive memory spikes (e.g., ~128MB overhead for a 5MB string).
- **Solution**: Replace the character table with direct `string.byte(str, index)` access during matching when Unicode is not required. Benchmarks prove that pairing `string.byte()` with numeric byte comparisons (`currentElement.byteValue == currentCharacter`) is not only vastly more memory efficient, but actually **faster** in total execution time than the table-split approach.
  - Store literal byte values during parsing instead of computing them during matching (e.g., `AST.Literal` stores `byteValue`).
  - Ensure this byte-oriented review applies to every node that performs character comparisons (literals, character classes, negated classes, ranges, escape sequences, `.`).
  - Preserve all current public API and matching semantics.

## Unicode Review Results

As requested, a benchmark was performed for Unicode mode to evaluate whether we should replace the current eager UTF-8 table-split approach with lazy decoding.

**Benchmark Results:**
A prototype lazy-decoder (`matcher_direct_unicode.lua`) was created that decodes UTF-8 bytes on demand during the matching loop using `string.byte` and `string.sub`, and compared against the current `utf8.transform` approach.

- **Large Unicode String (200k characters)**
  - Table Split: ~1.102s execution time, ~0.67 MB peak memory
  - Lazy Decode: ~1.110s execution time, ~0.92 MB peak memory (higher GC pressure)
- **Small String (10,000 iterations)**
  - Table Split: ~0.829s
  - Lazy Decode: ~0.934s

**Conclusion:**
Unlike non-Unicode mode where `string.byte()` provides ultra-fast integer comparisons, lazy Unicode decoding requires continuously extracting multi-byte strings via `string.sub()` during the innermost backtracking loops. This creates significant garbage collection pressure (allocating temporary strings), making lazy decoding slightly slower and more memory-intensive overall than just building the character table once.

Therefore, we will **retain** the current eager `utf8.transform` representation for Unicode mode. The byte-oriented target string representation refactor will apply **only** to non-Unicode execution.



#### [MODIFY] `expaghetti/matcher.lua` (Duplicated Capture Logic)
- **Issue**: Inside `coreTreeMatcher`, the logic to record group captures (inserting into `captureStarts` and `captureEnds`) is duplicated identically in two places: when returning from an `outerTreeReference` (lines 438-457) and at the end of the normal execution flow (lines 476-493).
- **Solution**: Extract this capturing logic into a single internal helper function or method on `MatchState` (e.g., `state:recordCapture(groupIndex, startIndex, endIndex)`).

#### [MODIFY] `expaghetti/ast.lua` (Inconsistent Node Shapes)
- **Issue**: AST nodes are built inconsistently. For example, `AST.Anchor` explicitly sets `quantifier = false`, while `AST.Set` and `AST.Group` simply omit the field.
- **Solution**: Standardize node structures. Remove `quantifier = false` from nodes that cannot be quantified, or establish a strict schema for all nodes.

### State Consolidation and Encapsulation

The current `MatchState` and `ParserState` objects have overlapping or loosely defined responsibilities. Specifically, `metaData` is often constructed inline (e.g., inside `matcher.lua` line 536 and `parser.lua` line 127) rather than encapsulated in the constructors.

To support compiled patterns being shared across multiple concurrent matches in the future, we will split state into clean categories:
1. **Immutable Compilation Metadata**: Data that does not change after parsing (e.g., AST, group names, flags).
2. **Mutable Execution State**: Data that changes during matching (e.g., captures, recursion depth, backtracking counters).
3. **Temporary Parser State**: Data only needed during the parsing phase (e.g., token streams, parse index).

#### [MODIFY] `expaghetti/match_state.lua`
- Move the inline construction of execution state (recursion limits, backtracking limits, root tree refs) from `matcher.lua` into `MatchState.new`.
- Add explicit helper methods to handle state tracking and limits:
  - `MatchState:incrementBacktrack()`: Increments `backtrackSteps` and returns `true` if limit exceeded.
  - `MatchState:enterRecursion()`: Increments `recursionDepth` and returns `true` if limit exceeded.
  - `MatchState:leaveRecursion()`: Decrements `recursionDepth`.
- Rename confusing or overly verbose fields:
  - `splitStr` -> `targetStringChars`
  - `strLength` -> `targetStringLength`
  - `groupCapturesInitStringPositions` -> `captureStarts`
  - `groupCapturesEndStringPositions` -> `captureEnds`
  - *Note: Capture state will remain as parallel tables to maximize performance.*

#### [MODIFY] `expaghetti/parser_state.lua`
- Move the inline construction of parser metadata (e.g., `groupNames`, `groupIndex`) from `parser.lua` into `ParserState.new`.
- Rename confusing fields to distinguish between tokenization and raw strings:
  - `expression` -> `patternChars`
  - `expressionLength` -> `patternLength`
  - `charactersIndex` -> `tokensLength` (since it tracks the length of the tokens array, not characters).

#### [MODIFY] `expaghetti/ast.lua`
- Clean up default fields: Currently, `AST.Anchor` sets `quantifier = false`. We will review all elements to ensure only quantified nodes store a quantifier field or default value.
- Re-evaluate boolean fields across nodes to see if specialized AST nodes or enums represent the state more cleanly (e.g. `isBeginning` on `Anchor`).

### Matcher and Parser Cleanup

The matcher and parser modules contain loose variable handling and scattered bounds checking that can be centralized.

#### [MODIFY] `expaghetti/matcher.lua`
- Update `MatchState.new` instantiation to no longer pass a massive inline `metaData` table. Pass `astMetaData` (formerly `parsedMetaData`) explicitly.
- Replace manual bounds checking for recursion and backtracking (e.g., `if state.metaData.backtrackSteps > state.metaData.maxBacktrackDepth`) with the new encapsulated `MatchState` methods.
- Update all variable references to the newly renamed `targetStringChars` and `targetStringLength`.
- Update capture array references to `captureStarts` and `captureEnds`.

#### [MODIFY] `expaghetti/parser.lua`
- Update `ParserState.new` instantiation to no longer require passing `metaData` initialized outside.
- Update variable references to `patternChars`, `patternLength`, and `tokensLength`.

---

### Magic Modules Consolidation

The magic modules must be updated to use the encapsulated methods on `MatchState` instead of mutating `metaData` directly.

#### [MODIFY] `expaghetti/magic/alternate.lua`
- Replace inline backtracking checks with `state:incrementBacktrack()`.

#### [MODIFY] `expaghetti/magic/group.lua`
- Replace inline recursion checks with `state:enterRecursion()` and `state:leaveRecursion()`.

#### [MODIFY] `expaghetti/magic/quantifier.lua`
- *Note: The logic resides in the matcher loop currently, so changes will mostly be in `matcher.lua` itself for quantifier logic.*
