# Workflow 12.3 — Architecture Review & Planning

The parser and matcher have now been migrated to the new architecture.

Before performing large-scale refactoring, review the architecture and produce a comprehensive implementation plan.

This is a design workflow.

Avoid making structural changes unless they are required to improve the planning process.

The objective is to understand the codebase, identify architectural improvements, and define the work that will be executed by the remaining workflows.

## Goals

Review the entire engine.

Understand how the parser, matcher, AST, helpers, magic modules, and state management interact.

Identify opportunities to simplify the architecture.

Produce a detailed refactoring plan.

## Review

Review, at minimum:

* parser
* matcher
* AST
* parser state
* matcher state
* helper modules
* magic modules
* enums
* project organization

## Identify

Review the code critically.

Do not assume the current implementation is optimal.

Document opportunities to improve:

* algorithms
* architecture
* module responsibilities
* state ownership
* API design
* AST structure
* parser flow
* matcher flow
* dispatch logic
* duplicated logic
* unnecessary abstractions
* unnecessary state
* large functions
* long parameter lists
* multiple return values
* magic values
* raw strings that should become enums
* inconsistent naming
* non-descriptive naming
* missing comments
* dead code
* obsolete helpers
* compatibility layers
* circular dependencies
* project organization

## Planning

Produce a detailed implementation plan for the remaining workflows.

The plan should include:

* parser improvements
* matcher improvements
* state consolidation
* architectural improvements
* cleanup tasks

Each improvement should include a brief explanation describing why the change is beneficial.

## Engineering Standards

Throughout the review:

* preserve the AST architecture
* do not redesign the engine around graphs, bytecode, NFAs, DFAs, or alternative execution models
* do not introduce new regex features, but fixing what is broken is acceptable
* preserve observable behavior in tests (currently at: `cd tests && lua init.lua`, and `cd tests && lua test_matcher.lua`)

## Architecture Constraints

The engine should continue to use an AST (tree) as its intermediate representation.

The AST structure, node types, metadata, and organization may be redesigned if doing so results in a simpler or more maintainable architecture.

Do not replace the AST with graphs, bytecode, NFAs, DFAs, or other execution models as part of this workflow.

When the AST changes:

- update the parser accordingly
- update the matcher accordingly
- update all affected tests
- remove obsolete AST structures
- remove compatibility code introduced solely to support the previous AST

## Deliverables

* Architecture review completed.
* Comprehensive refactoring plan.
* Prioritized implementation roadmap.

## Commit

Commit any documentation produced during this workflow.
