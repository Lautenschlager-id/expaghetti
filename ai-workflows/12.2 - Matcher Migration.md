# Workflow 12.2 — Matcher Migration

The parser migration has been completed.

Complete the migration to the new matcher architecture.

Do not introduce new regex features or change observable behavior.

## Goals

* Complete migration to the new matcher.
* Ensure every feature executes exclusively through the new matcher.
* Remove the legacy matcher.
* Leave a single execution pipeline.

## Tasks

Migrate every remaining implementation, including:

* literals
* escaped literals
* character classes
* sets
* quantifiers
* alternation
* groups
* captures
* backreferences
* assertions
* anchors
* recursion
* advanced regex features

Update every matcher consumer.

Remove:

* legacy matcher
* obsolete matcher helpers
* obsolete execution paths
* matcher compatibility code

Ensure every feature executes through the new matcher state.

## Code Quality

While modifying matcher code:

* Rename variables, functions, fields, and modules to descriptive names.
* Remove ambiguous variable names.
* Eliminate unnecessary temporary values.
* Simplify matcher logic.
* Simplify control flow.
* Reduce nesting where practical.
* Consolidate duplicated matcher logic.
* Remove dead code.
* Remove obsolete helpers.
* Remove temporary debug functionality.
* Remove logging and tracing used only during development.
* Improve naming consistency.
* Add comments explaining matcher algorithms, state transitions, recursion, captures, and backtracking where appropriate.
* Prefer self-documenting code whenever practical.

## Validation

* Complete test suite passes.
* No remaining references to the legacy matcher.
* Matching behavior is identical.

Throughout this workflow, continuously verify that the migration does not introduce regressions.

After completing each significant batch of changes:

* Run `cd tests & lua init.lua` to ensure the project builds and executes successfully.
* Run `cd tests & lua test_matcher.lua` and ensure the complete matcher test suite passes.
* Run any other relevant test suites affected by the modified code.
* Fix regressions before continuing with the migration.
* Do not defer failing tests to later workflows.

The project should remain in a working, releasable state throughout the migration rather than only at its completion.

## Deliverables

* New matcher exclusively used.
* Legacy matcher removed.
* Single execution pipeline.

## Commit

Commit progress in logical batches throughout this workflow rather than waiting until the very end.

Each commit should represent a coherent, working unit of work.

After each batch:

* ensure the project builds successfully
* run `cd tests & lua init.lua`
* run `cd tests & lua test_matcher.lua`
* run any other relevant test suites affected by the changes
* verify all modified tests pass
* verify no regressions were introduced

This ensures that if the execution quota is reached or the workflow is interrupted, there is always a clean, working commit from which to continue.

Before completing the workflow:

* ensure the project builds successfully
* ensure the complete test suite passes
* ensure no dead code remains in the modified areas
* ensure no obsolete debug features remain in the modified areas
* ensure documentation reflects the architectural changes

Create a final commit summarizing the completed workflow.
