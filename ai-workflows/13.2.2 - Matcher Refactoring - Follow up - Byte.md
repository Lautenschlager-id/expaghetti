# Workflow 13.2.2 — Byte-Oriented Matcher Execution

Implement a byte-oriented execution path for non-Unicode matching while preserving the current matcher architecture established in Workflow 13.2.

The primary objective of this workflow is **not** simply to reduce memory allocations. The goal is to introduce a second execution representation that integrates naturally with the existing architecture, minimizes branching, and preserves readability.

The matcher should remain an execution engine rather than becoming aware of multiple internal representations.

---

# Objectives

Implement byte-oriented execution for non-Unicode patterns while ensuring:

- Zero behavioral regressions.
- Minimal matcher changes.
- Minimal runtime branching.
- Clear ownership of responsibilities.
- No duplicated matcher implementation.
- Full compatibility with Unicode execution.

The resulting architecture should feel like a natural extension of the matcher rather than a special-case optimization.

---

# Architectural Review

Before implementing any changes, review the current matcher architecture established during Workflow 13.2.

Determine whether introducing byte-oriented execution requires any additional abstractions.

If a cleaner abstraction naturally emerges during implementation, prefer that design over mechanically following this implementation plan.

The implementation plan is a guide, not a constraint.

---

# Execution Representation

Implement two execution representations:

## Unicode execution

Current behavior remains unchanged.

Target string representation:

- UTF-8 character array.

AST representation:

- Existing string values.

Character comparisons:

- String-based.

---

## Byte execution

When the Unicode flag is absent:

Target string representation:

- Raw Lua string.

Character access:

- `string.byte`.

AST representation:

- Byte-oriented metadata.

Character comparisons:

- Integer-based.

The matcher should operate on comparable execution values without requiring pervasive knowledge of whether execution is string-based or byte-based.

---

# Target Access Abstraction

Review whether target character access should be centralized.

The matcher should avoid scattered logic such as:

```lua
if unicode then
    ...
else
    ...
end
```

throughout the execution hot path.

Instead, determine whether a dedicated abstraction owned by `MatchState` (or another appropriate owner) can provide the matcher with comparable target elements while hiding the underlying representation.

This abstraction should remain small and focused.

Avoid creating unnecessary wrapper layers.

---

# AST Execution Metadata

Review which execution metadata should be precomputed during compilation.

Examples include:

- byte values
- case-folded byte values
- range metadata
- lookup tables

Only introduce metadata that is actually consumed by the matcher.

Avoid eagerly caching values that provide no measurable benefit.

The AST should remain a compact compiled representation.

---

# Literal Matching

Review literal matching under both execution modes.

The matcher should avoid performing runtime conversions such as:

- `string.byte`
- `string.lower`
- `string.upper`

inside hot execution paths whenever practical.

Prefer precomputed execution metadata.

---

# Character Sets

Perform a complete review of character set execution.

This includes:

- literal members
- escaped literals
- predefined classes
- ranges
- negated sets

Review both execution modes independently.

The byte-oriented representation should naturally support efficient membership testing without introducing runtime type checks.

---

# Case-Insensitive Matching

Perform a complete review of `flag.i`.

This review should include:

- literals
- character sets
- character ranges
- predefined classes
- escaped literals

Determine where additional work should occur.

Whenever practical, perform normalization during compilation rather than during matching.

The matcher should remain as branch-free as possible.

---

# Runtime Branching Review

Review the final implementation for unnecessary runtime branching.

Examples include:

- `type(...)`
- byte/string comparisons
- repeated Unicode checks
- duplicated execution paths

Eliminate branching where doing so improves readability without sacrificing maintainability.

The matcher should not contain two separate implementations.

---

# Responsibility Review

Review ownership after implementation.

Desired responsibilities:

**MatchState**

- execution state
- target access
- execution representation

**Matcher**

- traversal
- recursion
- backtracking
- quantifiers
- execution flow

**AST**

- immutable compiled representation
- execution metadata

**Magic modules**

- element-specific parsing
- element-specific matching

No module should perform work that naturally belongs to another.

---

# Duplication and Conversion Review

During implementation, continuously review the codebase for duplicated execution logic introduced by supporting multiple execution representations.

In particular, avoid patterns such as:

- Repeated `type(...)` checks.
- Repeated `string.byte(...)` conversions.
- Repeated `string.char(...)` conversions.
- Repeated `string.lower(string.char(...))` or equivalent conversion chains.
- Repeated Unicode/byte branching.
- Repeated case-normalization logic.

If the same conversion or branching logic appears in more than one place, stop and determine whether a dedicated abstraction or helper should exist instead.

The objective is not merely to reduce duplicated lines of code, but to centralize execution-specific knowledge.

The matcher and magic modules should operate on well-defined execution values rather than performing ad hoc conversions throughout the execution path.

Prefer introducing a small, cohesive abstraction over duplicating conversion logic across multiple modules.

Any helper introduced should:

- Own a single responsibility.
- Hide execution representation details.
- Reduce duplicated logic.
- Improve readability.
- Be reusable by multiple matcher components.

Avoid introducing helpers that merely relocate complexity without reducing it.

# Correctness Validation

Run the complete test suite.

Pay particular attention to:

- `flag.i`
- Character sets.
- Backtracking.
- Captures.

# Final Architectural Review

After implementation, perform a final architectural review.

Verify that:

- Byte execution feels like a first-class execution mode.
- The matcher remains primarily concerned with traversal.
- No abandoned abstractions or temporary compatibility layers remain.
- The implementation is cleaner than the architecture that existed before the optimization.

If a cleaner design is discovered during implementation, prefer that design even if it differs from the original proposal.

# Complete Matcher Review

This workflow introduces a second execution representation for the matcher.

Do **not** limit the review to the files already listed in the implementation plan.

Perform a complete architectural review of the matcher and all matcher-related modules to identify any code that should participate in the byte-oriented execution model.

This review should include, but is not limited to:

## Core Matcher

Review:

- `matcher.lua`
- `match_state.lua`

Verify:

- Character access.
- Execution state.
- Runtime branching.
- Target representation.
- Helper opportunities.
- Duplicated execution logic.

---

## AST

Review:

- `ast.lua`

Verify:

- Execution metadata.
- Helper methods.
- Ownership of execution-specific data.
- Unused metadata.
- Opportunities to centralize execution representation.

---

## Magic Modules

Review every magic module that participates in matching, including:

- `anchor.lua`
- `any.lua`
- `alternate.lua`
- `balanced.lua`
- `boundary.lua`
- `capture_reference.lua`
- `group.lua`
- `literal.lua`
- `position_capture.lua`

For each module, verify:

- Whether byte-oriented execution requires changes.
- Whether duplicated conversion logic exists.
- Whether duplicated branching exists.
- Whether helper methods should be introduced.
- Whether execution representation leaks into the module.
- Whether responsibilities remain well separated.

No module should independently invent its own byte/string conversion logic.

---

## Character Classes

Review all character class implementations.

Verify:

- Literal classes.
- Built-in classes.
- Ranges.
- Negated ranges.
- Balanced matching.
- Case-insensitive behavior.

Ensure Unicode and byte execution produce identical behavior.

---

## Conversion Review

Review the entire matcher codebase for repeated execution conversions.

Examples include:

- `string.byte(...)`
- `string.char(...)`
- `string.lower(...)`
- `string.upper(...)`
- `string.lower(string.char(...))`
- `string.upper(string.char(...))`
- Byte/string normalization.
- Runtime type checks.

If identical conversion logic appears more than once, stop and determine whether a shared abstraction or helper should exist.

Avoid copying conversion code across multiple modules.

---

## Runtime Branching Review

Review every matcher component for duplicated runtime branching.

Examples include:

- `if unicode then`
- `if type(...) == "number"`
- Byte/string comparisons.
- Execution-mode switches.

The matcher should not gradually become two implementations sharing the same file.

Where practical, centralize execution representation behind well-defined abstractions.

---

## Helper Review

Continuously review whether helper functions should be introduced.

Good helpers should:

- Remove duplicated code.
- Hide execution representation.
- Improve readability.
- Reduce branching.
- Be reusable by multiple matcher modules.

Avoid helpers that merely wrap one or two lines without reducing architectural complexity.

---

## Final Architecture Review

After implementation, review the entire matcher architecture.

Verify that:

- The matcher remains an execution engine.
- `MatchState` owns execution state.
- AST owns execution metadata.
- Magic modules own element-specific matching.
- Execution representation is centralized.
- No duplicated conversion logic remains.
- No abandoned abstractions remain.

The implementation should be evaluated on the quality of the final architecture rather than how closely it follows the original implementation plan.

## Character Set Compilation Review

Perform a complete review of how character sets are compiled.

Avoid eagerly transforming or expanding set representations before it is clear which execution flags apply.

In particular, review interactions with:

- `flag.i`
- Unicode execution
- Byte-oriented execution
- Shared predefined classes and enums

Compiled character sets must remain independent of one another.

For example, a regex compiled with `flag.i` must never mutate or influence the compiled representation used by another regex compiled without `flag.i`.

Likewise, predefined character classes, enums, and other shared structures must remain immutable.

If byte-oriented or case-insensitive execution requires additional lookup tables or expanded representations, they should be created per compiled regex (or lazily when appropriate), never by mutating globally shared data.

The implementation should preserve referential safety while still minimizing duplicated work.
