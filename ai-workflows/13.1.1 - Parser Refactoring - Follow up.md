## Follow-up: Parser Element Abstraction Review

> [!IMPORTANT]
> The tokenizer removal significantly simplified the parser architecture and eliminated an unnecessary intermediate representation. However, the refactor appears to have shifted part of the tokenizer's responsibilities into multiple parser modules, particularly around escape handling.
>
> This follow-up review aims to recover that lost abstraction **without reintroducing the tokenizer or materializing a token array**.

## Objectives

Review the parser implementation and determine whether escape handling and logical element parsing can be centralized while preserving the current streaming parser architecture.

The goal is **not** to reintroduce `tokenizer.lua`, but to avoid duplicated lexical analysis logic across parser modules.

---

## Escape Handling Review

Review all parser components and identify places where they independently determine whether a character is escaped.

Examples include:

- Checking whether the current character is an escape character.
- Calling `Escaped.parse()` directly.
- Manually advancing indexes to skip escape sequences.
- Determining whether escaped characters should be interpreted as literals or parser elements.

Determine whether this logic can be centralized.

---

## Logical Element Abstraction

Evaluate introducing a lightweight parser helper responsible for reading **exactly one logical pattern element** from the current parser position.

For example, instead of exposing raw characters directly to every parser component:

```lua
local currentCharacter = state.patternChars[index]
```

consider exposing an abstraction similar to:

```lua
local nextIndex, element = state:readElement(index)
```

or an equivalent design.

The abstraction should return a normalized parser element, allowing parser modules to reason about logical elements rather than raw characters and escape sequences.

This helper should **not** allocate or cache a token list. It should operate lazily, reading only the requested element.

---

## Parser Simplification Review

Review parser modules for duplicated lexical analysis.

Examples include:

- Repeated checks for escape characters.
- Multiple calls to `Escaped.parse()`.
- Duplicate logic for peeking the next logical element.
- Manual index manipulation to account for escaped characters.

Determine whether these responsibilities can be delegated to the proposed element reader.

---

## Responsibility Separation

Review whether parser modules are beginning to mix lexical analysis with grammar parsing.

The desired responsibility split is:

- **Element reader:** Understands raw pattern characters, escape sequences, and logical parser elements.
- **Parser modules:** Understand grammar, AST construction, precedence, quantifiers, groups, sets, etc.

Parser modules should not need to understand how escape sequences are represented internally.

---

## Validation

Any proposed abstraction should satisfy the following:

- Do **not** reintroduce `tokenizer.lua`.
- Do **not** allocate an intermediate token array.
- Preserve the current streaming parser architecture.
- Reduce duplicated escape handling logic.
- Simplify parser modules.
- Improve maintainability without changing parser behavior or public APIs.

Only introduce the abstraction if it provides a measurable improvement in readability, responsibility separation, and long-term maintainability.
